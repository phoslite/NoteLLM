- **日期**：2026-08-05
- **状态**：调研结论，阶段 2/4 需用户确认取舍
- **关联文档**：[docs/性能优化路径.md](./性能优化路径.md)

## 结论速览

- `backend/data` 实测总量约 **510 MB**，其中页图 305.3 MB（60.5%）+ 原文件 197.1 MB（39.0%）合计占 99.5%。
- 最大浪费点是 `c29b17d1186c`（98 页扫描书，2122×3012 分辨率，单页均值 999 KB，合计 95.70 MB）。
- 推荐按阶段 0~4 实施：WAL 回收 → JPEG q85 重渲（-76~98 MB）→ 双层分级渲染（基础层封顶 + 放大按需高清，净 -88~97 MB）→ 按需渲染+LRU（上限 -260 MB）→ 可选删原文件（-197 MB）。
- 组合上限：全库可从 **510 MB 降至 ~115 MB（-77%）**。**注意：该上限包含牺牲放大清晰度的选项（q80、裸分辨率封顶）**；高清零妥协前提下（见第 4 章），页图部分约为 **305 → 208~217 MB（-30%）**。
- **警示**：`03613c0ac055`（100.7 MB 原文件）页图从未渲染，任何涉及原文件的清理必须先校验页图齐全，否则该书不可读。

## 2. 缓存可再生性分类

| 分类 | 内容 | 再生条件 |
|---|---|---|
| **不可再生** | 原文件（PDF/EPUB/MD/TXT）、`annotations/` 涂鸦 JSON、DB 中笔记/书签/对话/画像 | 丢失即永久丢失 |
| **可再生（免费）** | `pages/` 页图、`cover.jpg`、`local_text/` + FTS 索引、`data/cache/graph_clusters.json` | 由原文件重算，仅耗 CPU/时间 |
| **可再生（花钱）** | `page_text/*.md`（视觉 API token）、`llm_caches`（LLM token） | 重建需重新调用付费 API |

关键依赖关系：**所有「免费可再生」项都依赖原文件**；原文件一旦删除，页图/封面/FTS 将不可重建。

## 4. 高清前提下的压缩方案（双层分级渲染）

> 本章为任务 #25 专项调研结论（2026-08-05）：在「不降低放大阅读清晰度」的硬约束下重新评估页图压缩空间。基准数据：页图 305.3 MB / 1375 页 / 均值 233 KB（见第 1 章盘点）。

### 4.1 「高清」的客观定义：前端显示链路结论

显示宽度如何确定（代码证据）：

| 环节 | 事实 | 证据位置 |
|---|---|---|
| 三栏布局 | 左栏 `width: 25%; min-width: 280px`，右栏 AI 面板 `width: 30%; min-width: 320px`，中栏 `flex: 1` | `frontend\src\components\ReaderLeftPanel.vue` L73-77、`ReaderChatPanel.vue` L136-140、`ReaderView.vue` L603-612 |
| 阅读区留白 | `.reading-scroll { padding: 18px 40px 48px }` + 垂直滚动条（约 12~17px） | `ReaderView.vue` L641 |
| 适配模式 | `pageZoom='fit'` 时 `max-width: 100%`，即页图显示宽度 = 容器内容宽 | `ReaderView.vue` L55-59、L646 |
| DPR 参与 | **前端代码中没有任何 `devicePixelRatio` 引用**（全 frontend/src grep 无命中），浏览器自行按 DPR 缩放位图 | grep 实测 |

**推导公式**：显示 CSS 宽度 ≈ 窗口宽度 × 0.45 − 80px（左右 padding）− 滚动条。

| 窗口宽度 | 页图显示 CSS 宽 | ×DPR1.5 | ×DPR2 |
|---|---|---|---|
| 1280（面板触底 min-width 280+320） | ≈ 600 px | 900 | 1200 |
| 1920（常见 1080p） | ≈ 770 px | 1155 | 1540 |
| 2560（2K） | ≈ 1050 px | 1575 | 2100 |
| 3840（4K，DPR1） | ≈ 1630 px | — | — |

**结论**：正常阅读（fit 模式）所需像素上限 = 容器 CSS 宽 × DPR，实测场景封顶约 1600~1700px（4K@DPR1 或 2K@DPR1.5 极限）；**取 1800~2000px 封顶即可覆盖全部常规设备**。超出部分（如 c29b 的 2122px，以及用户主动放大到 2~3× 时需要的 3000~6000+px）**只在用户主动放大时才需要**——这是分级渲染的理论基础。

### 4.2 现状缩放机制事实

- 缩放为**纯 CSS 宽度调整（0.5~3 倍）**：`zoomBy()` 将 `pageZoom` 限定在 **0.5~3**，显示宽度 = `naturalWidth × pageZoom`（`ReaderView.vue` L55-65）。**放大不会重新请求更高分辨率图片**，只是拉伸现有位图；缩放基准是「当前缓存图的原始宽度」，不是 PDF 源分辨率。
- 预载：当前页前后各 1 页 eager 预载，请求的就是默认 `/api/books/{id}/pages/{N}`，无分辨率参数（L470-473）。
- 路由侧也无参数：`backend\app\api\routes\books.py` L155-164 仅返回 `get_or_render_page()` 的单一文件，`Cache-Control: max-age=600`。

### 4.3 双层分级渲染设计

- **存储双层**：`page_XXX.jpg`（基础层 ≤1600~1800px，q85）+ `page_XXX_hd.jpg` 或 `hd/` 子目录（原始高清，按需生成）。需扩展 `media_service.py` 硬编码的 `PAGE_IMAGE_PATTERN`。
- **路由扩展**：`GET /pages/{N}?w=hd`（或子路径），命中已有高清文件直接 FileResponse，否则按需渲染后返回。
- **前端放大触发**：`zoomBy`/zoom 变更时计算 `naturalWidth × zoom × devicePixelRatio`，超过基础层像素宽 ×1.2 时异步请求高清图，加载完成后换 `src`（建议双缓冲：新建 Image 预载成功后替换，避免闪白）。语义需调整：分级后 zoom 基准变为高清层目标宽度，否则「1:1」按钮含义漂移。
- **放大预渲相邻页**：放大触发时用现有 `page_render_concurrency=4` 线程池模式**预渲相邻 ±1 页高清**，连续放大翻页无感。
- **单页重渲延迟评估**：PyMuPDF 单页渲染 50~200ms（大幅扫描页偏上端）+ JPEG 编码；用户主动放大属低频操作，可接受。
- **复用现有机制**：`get_or_render_page()`（`backend\app\services\book_pages.py` L9-33）已具备「缺页即渲、低于目标宽度 85% 删除重渲」的升级骨架——天然支持按需补高清，但其目标是单一全高清宽度（`pdf_page_target_width` = 内嵌原图宽度，`backend\app\parsers\pdf.py` L44-62），需改为双层目标。
- **重要风险**：若只做分辨率封顶而不改 `book_pages.py` L20-22 的低清判定，每次请求都会判定「现存图 < 原图目标×0.85」→ 删了重渲、重渲又被判定低清，形成死循环式重复渲染。分级改造必须同步把基础层目标改为 `min(native, cap)`。

### 4.4 各书节省量估算（基于实测分辨率分布）

JPEG 体积近似 ∝ 像素面积 × 质量系数（q90→q85 ≈ ×0.75）：

| 书 | 现状 | 基础层 1600px + q85 后 | 说明 |
|---|---|---|---|
| c29b（98 页，2122px，95.7MB） | 999 KB/页 | 95.7 × (1600/2122)² × 0.75 ≈ **41 MB** | 面积比 0.569，最大受益者 |
| 38367（538 页，1080px，162.7MB） | 309 KB/页 | ×0.75 ≈ **122 MB** | 宽度低于封顶，仅质量收益 |
| c76a（409 页，≤1239px，24.6MB） | 61 KB/页 | ≈ **18.5 MB** | 仅质量收益 |
| 4a97（330 页，最大 1922px，22.3MB） | 69 KB/页 | ≈ **16 MB** | 少量大页吃面积收益 |

**基础层合计 ≈ 197 MB（−108 MB，−35%）**；高清层按 10~20% 页面被实际放大计，额外开销约 +10~20 MB（几乎全部来自 c29b）。**净结果 ≈ 208~217 MB，节省 −88~97 MB**，且放大阅读清晰度与现状完全一致（高清层就是现在的原图分辨率）。

### 4.5 格式与质量空间

**环境实测**：

- **PyMuPDF 版本 = 1.28.0**（`backend\.venv` pip show 实测），`pyproject.toml` 声明 `pymupdf>=1.28`。
- **WebP：`pix.save()` 原生不支持**（MuPDF 仅原生输出 PNG/JPEG/PNM/PSD/PS/JPX）；文档明确 WebP 需走 `pix.pil_save()`/`pil_tobytes(format="WEBP")`，**依赖 Pillow**。而当前 venv **未安装 Pillow**（pip show 实测 not found，pyproject 亦未声明）→ 走 WebP 需先新增依赖。
- **AVIF**：PyMuPDF 无任何支持，需 pillow-avif-plugin 之类三方件，编码速度比 JPEG 慢约 10~50×，对按需渲染延迟（50~200ms 预算）是致命的。**结论：不建议**。

**JPEG 质量曲线（文献经验值）**：

| 档位 | 相对 q90 体积 | 文字页视觉影响 |
|---|---|---|
| q85 | −25~35% | 1:1 放大细笔画处有极轻微振铃，正常显示不可察——**「高清无损感」安全下限** |
| q82 | −30~38% | 折中档，扫描/照片页几乎无感，纯文字锐利边缘需抽检验收 |
| q80（旧方案阶段 1） | −35~40% | 高分屏 1:1 可见块状伪影增多，与「高清」要求存在张力 |

**结论**：高清前提下把旧方案阶段 1 的 q80 上调为 **q85（稳妥）或 q82（需抽检验收）**；扫描照片页（c29b）对质量下降比文字页更宽容。

### 4.6 压缩菜单汇总

| # | 方案 | 预期节省（基于 305MB） | 成本 | 高清影响 | 叠加关系 |
|---|---|---|---|---|---|
| **1** | **质量 q90→q85/q82**（改 `parsers/pdf.py` 默认值 + 批量重渲） | **−76~98 MB（−25~32%）** | 低 | 无（正常阅读零损失） | 与所有项叠加 |
| **2** | **分级渲染：基础层 ≤1600~1800px + 放大按需高清** | **净 −88~97 MB**（基础层 −108，高清层回补 +10~20） | 中（前后端联动 + book_pages 判定改造） | 无——放大时按需高清兜底 | 与 1 叠加；**替代**旧方案 B 的裸封顶 |
| 3 | WebP（装 Pillow，`pil_save`） | 在 1+2 基础上再 −25~30% | 高（依赖 + 文件名硬编码 + vision mimetype + 存量迁移） | 无 | 叠加，置最后 |
| 4 | 高清层 LRU 淘汰（配合 #2，长期未放大的高清文件回收） | −10~20 MB | 低 | 无 | #2 的附属件 |
| ✗ | 裸分辨率封顶 1600px 无高清兜底（旧方案 B/阶段 2） | −45~60 MB | 中 | **2K 屏放大变糊——与高清要求冲突** | 被 #2 取代，**不推荐单独实施** |
| ✗ | q≤80（旧阶段 1 参数） | 更多 | 低 | 1:1 伪影可见 | 高清前提下建议上调至 q82~85 |
| ✗ | AVIF | — | 高 | 编码慢拖累按需渲染 | **不建议** |

### 4.7 推荐组合

- **推荐（高清零妥协）**：#1(q85) + #2(基础层 1600px + 按需高清) + #4 → **305 MB 降至约 208~217 MB，节省约 −90~97 MB（−30%）**；若质量取 q82 可再省 ~13 MB。
- **进阶（可接受引入 Pillow）**：叠加 #3 WebP → **降至约 145~155 MB（−50%）**。
- 对比旧方案（阶段 1 q80 + 阶段 2 裸封顶，合计 −152~167 MB）：本方案少省约 55~70 MB，换来的代价是**放大阅读清晰度与现状完全一致**，符合「高清阅读」硬约束。
- 注意：本菜单只覆盖 305MB 页图；原文件 197MB（旧阶段 4）、WAL 回收（阶段 0）属独立决策，不在高清约束范围内。

### 4.8 实施注意点

1. `book_pages.py` L20-22 的低清升级判定必须与封顶值同步改造，否则封顶页会被反复删除重渲（死循环，见 4.3）。
2. 前端 zoom 以 `naturalWidth` 为基准，分级后需重新锚定语义，否则「1:1/适配」按钮显示百分比失真（`ReaderView.vue` L55-65）。
3. 高清图换 src 时建议双缓冲预载替换，避免闪白；`Cache-Control: max-age=600`（books.py L164）对同一路径换内容场景需注意（用不同 URL/参数区分两层可天然规避）。
4. `vision_extract.py` 读基础层 jpg 即可满足视觉提取，无需高清层，分级不影响该链路（只要文件名约定保持 `.jpg`）。
5. 涂鸦坐标为归一化值（`useReaderDoodle.ts`），分辨率/层级变更不受影响；`pageDisplaySize` 基于 `clientWidth`（L54-58），同样自适应。
