### 1.3 Top 8 最需关注问题

后端 3 条高严重度：

1. **【后端·高】compute_cross_book_graph 长写事务横跨 LLM 打分**（`services/graph/cross_book.py`）——全量重建图谱时 SQLite 写锁被占用数分钟，其他写操作 30s busy timeout 后报「database is locked」，进度保存/笔记/导入全部失败，是唯一会「锁死整个应用」的问题。
2. **【后端·高】assets summarize 任务会话从不 close**（`api/routes/assets.py:26`）——每次触发 summarize/archive 后台任务都泄漏一个数据库会话，长期运行必然耗尽连接，属确定性资源泄漏。
3. **【后端·高】导入同步阶段串行渲染全部 PDF 页图**（`services/import_service.py`）——「秒回」承诺实际失效，千页书同步阶段阻塞分钟级，且后台阶段还会重复渲染一遍，双倍耗时。

前端 3 条高严重度：

4. **【前端·高】useReaderPageCache 可见性暂停轮询后永不恢复**（N-1）——流式生成期间切走标签页，监听器被移除后轮询永久停摆，页缓存不再落库，是真实可复现的 bug。
5. **【前端·高】ReaderView loadChapter 无请求序号防护**（N-11）——网络慢时快速切章节，旧响应覆盖新内容，用户读到错误章节且阅读进度随之写错。
6. **【前端·高】MdRender 每实例新建 markdown-it + KaTeX 每次异步 import**（N-22）——长章节数百实例叠加初始化开销，首段渲染被异步 import 阻塞，是阅读页性能的结构性瓶颈。

综合最关键的 2 条（跨端联动）：

7. **【综合】前端任务轮询体系碎片化 + 后端任务幂等防护不一致**——前端 5 处私有轮询实现（部分不可取消、部分卸载泄漏，见 N-19/N-31/N-2/N-10）与后端 assets 路由缺 find_active 幂等（后端问题 4）同属「后台任务」链路短板，任一端出错用户都只能看到卡死或重复提交，需一并治理。
8. **【综合】测试基线盲区恰好覆盖最高风险链路**——后端导入链路（全系统最复杂链路，零测试）与前端 composables 层（8 件套全部零测试）是问题 1/2 与 N-1/N-4 等 bug 的藏身处，修复高危问题前应先补最小测试保护。

## 二、后端潜在问题清单（21 条）

> 以下条目按模块分组，位置均相对于 `backend/app/`。已排除既有审查报告登记的已知问题。

### 2.1 导入链路（import_service / assets 路由）

**问题 1｜同步上传阶段串行渲染全部 PDF 页图（严重度：高）**
- 位置：`services/import_service.py` import_book_file 第 111-112 行；`_import_background` 第 155 行。
- 问题：同步上传阶段未传 workers 串行渲染全部 PDF 页图，后台阶段又并发重渲染一遍，parse_book 在后台第三次读 PDF。
- 触发条件：上传任意 PDF。
- 影响：「秒回」承诺失效（千页书同步阶段阻塞分钟级）；页图渲染双倍耗时。
- 修复方向：删除同步阶段的 render_pdf_pages，页图全部交给后台任务；解析只做章节抽取。

**问题 2｜解析失败产生孤儿目录（严重度：中）**
- 位置：`services/import_service.py`。
- 问题：文件已 move 进 `data/books/<file_id>/` 后才 parse，失败时无 Book 记录也无清理路径。
- 触发条件：上传损坏的 EPUB/空 TXT/乱码文件。
- 影响：磁盘垃圾目录累积，重复上传同文件 hash 去重判定受干扰。
- 修复方向：解析失败时 rmtree 该子目录；或先解析临时区再 move。

**问题 3｜summarize 任务会话从不 close（严重度：高）**
- 位置：`api/routes/assets.py` summarize 路由第 26 行。
- 问题：`lambda: generate_rag_skill(SessionLocal(), book_id=...)` 会话从不 close（已知报告只登记了「SessionLocal 直连」分层问题，此处是确定性资源泄漏）。
- 触发条件：每次触发 summarize/archive 后台任务。
- 影响：连接与会话逐次泄漏，长期运行耗尽连接。
- 修复方向：任务函数内部自建会话并 try/finally close。

**问题 4｜assets 路由无 find_active 幂等防护（严重度：中）**
- 位置：`api/routes/assets.py` summarize/archive。
- 问题：graph 路由的 `_submit_graph_task` 有幂等防护，此处缺失。
- 触发条件：前端双击/重复点击。
- 影响：同一书两个 RAG 生成任务并发写同一 BookAsset，结果互相覆盖。
- 修复方向：复用 find_active(type, related_id) 防护模式。

### 2.2 知识图谱（graph 包）

**问题 5｜长写事务横跨 LLM 打分（严重度：高）**
- 位置：`services/graph/cross_book.py` compute_cross_book_graph。
- 问题：第 58 行 delete BookRelation 开启写事务，第 103 行 LLM enrich（最多 40 对、可达分钟级），第 108 行才 commit；对比 `incremental_cross_book_graph` 第 158 行在 LLM 之前 commit（正确做法）。

**问题 6｜全量重建清空人工反馈（严重度：中）**
- 位置：`services/graph/cross_book.py`。

**问题 7｜GET 端点内写库（严重度：中）**

### 2.3 AI / 对话（ai/client.py / chat_service / rag_router）

**问题 11｜build_catalog 无排序后截断 150（严重度：低）**

## 三、前端潜在问题清单（N-1 ~ N-34）

> 以下条目按模块分组，位置均相对于 `frontend/src/`。已比对既有审查报告全部已知条目，以下均为增量新发现。

### 3.1 composables

**N-1｜useReaderPageCache.ts：可见性暂停轮询后永不恢复（严重度：高，真实 bug）**
- 问题：`onTaskPollVisibility` 在页面 hidden 时调用 `stopPolling()`，而 `stopPolling` 内部会 `removeEventListener('visibilitychange', ...)`，监听器被移除后页面恢复 visible 时轮询无法再启动。
- 触发条件：流式生成期间切走标签页/最小化。
- 影响：页图缓存轮询永久停摆，当前任务后续页缓存不再增量落库，直到下次手动触发。
- 修复方向：暂停用独立的 pause 标志位，visibilitychange 监听的生命周期与轮询开关解耦。

**N-2｜useReaderPageCache.ts：无导出清理入口，卸载后轮询泄漏（严重度：中）**
- 问题：模块未导出 stop/dispose，ReaderView 的 `onBeforeUnmount` 无法停止 2s 历史补偿轮询。
- 触发条件：任务进行中离开阅读页。
- 影响：离开页面后每 2s 一次请求持续打到任务终态；多次进出页面可叠加多个轮询循环。
- 修复方向：导出 dispose 并在 onBeforeUnmount 调用，或把轮询句柄收敛到 composable 返回值。

**N-3｜useReaderAi.ts：卸载无清理（SSE 不 abort、历史轮询定时器残留）（严重度：中）**
- 问题：流式回答中离开页面不会中止 fetch 流；`pollTimer`（2s 历史轮询 setInterval）只在请求 promise 的 finally 中清除，组件卸载不触发。
- 触发条件：AI 回答流式输出中途切章/切书/离开。
- 影响：网络与后端推理继续空耗；卸载后定时器继续轮询并尝试写已卸载组件的状态。
- 修复方向：暴露 `dispose()`（abort + clearInterval），ReaderView onBeforeUnmount 统一调用。

**N-4｜useReaderAi.ts：历史合并去重条件过弱，产生重复气泡（严重度：中）**
- 问题：`loadChatHistory` 合并服务端历史与本地消息时仅按「角色 + 内容全等」去重；流式落库内容往往比本地截断内容更长。
- 触发条件：流式中断/刷新后重新拉历史。
- 影响：同一回答出现两条内容相近的气泡。
- 修复方向：引入消息 id 或 stream_key 作为去重键。

**N-5｜useReaderDoodle.ts：deep watch 在数据加载时也触发回写（严重度：中）**
- 问题：`watch(doodleElements, deep)` 对 `loadDoodle` 赋新值同样触发，每切一页先产生一次无意义 PUT。
- 触发条件：每次翻页加载涂鸦数据。
- 影响：无效写请求放大；与真实编辑写回竞争时可能覆盖时序。
- 修复方向：加载期置抑制标志，或改用「加载完成后才激活 watch」。

**N-6｜useReaderDoodle.ts / PageDoodleCanvas.vue：全局选择器 `.page-img`（严重度：低）**
- 问题：`document.querySelector('.page-img')` 获取图片尺寸，依赖页面中该元素唯一。
- 触发条件：未来出现第二个 `.page-img`（如预览缩略图、打印视图）。
- 影响：静默取错元素导致坐标换算错误，涂鸦错位。
- 修复方向：改为模板 ref 注入。

**N-7｜useReaderNotes.ts：高亮应用复杂度 O(段落 × 笔记 × 文本长度)（严重度：中）**
- 问题：`applyHighlights` 对每条笔记在每一段内做 TreeWalker 全文本扫描。
- 触发条件：长章节 + 数十条笔记。
- 影响：章节渲染后高亮阶段明显卡顿（与已知虚拟滚动问题不同源）。
- 修复方向：笔记按段落索引预分桶，或只对笔记记录的 para_pos 段落扫描。

**N-8｜useReaderNotes.ts：jumpToNote 启发式匹配可能跳错段落（严重度：中）**
- 问题：用 `b.includes(quote) || quote.includes(b.slice(0,50))` 定位段落，短引用/常见句式（如 50 字内高频开头）会命中错误段落。
- 修复方向：优先使用笔记自带的 para_pos 精确跳转，includes 仅作兜底。

**N-9｜useReaderProgress.ts：两个小缺陷（严重度：低）**
- 问题：`checkAutoRead` 同时被 1s 定时器和每次 scroll 事件调用，滚动时重复计算；`resetForBook` 不清 `visibleAccumMs`，切书后残留上一本的可视累计时长。
- 修复方向：scroll 仅置脏标记由定时器结算；resetForBook 补清零。

**N-10｜useReaderArchive.ts：卸载后轮询不终止（严重度：中）**
- 问题：120 次 ×1.5s 内联轮询无取消机制，归档轮询中离开页面仍继续，且结束后仍回调 `onDone` 触发已卸载组件的刷新。（与既有报告 B-1「轮询实现重复」不同：此处登记生命周期问题。）
- 修复方向：轮询改走 `waitForTask` 并接入组件卸载信号。

### 3.2 views

**N-11｜ReaderView.vue：loadChapter 无请求序号防护（竞态）（严重度：高）**
- 问题：快速连续切章节时，`getChapterContent` 若乱序返回，旧章节内容会覆盖新章节。对照：`useReaderAi.loadChatHistory` 已用 `historySeq` 做了同样防护，说明模式已知但章节加载漏用。
- 触发条件：网络慢时快速点上一章/下一章。
- 影响：正文与目录选中项不一致，用户读到错误章节且进度可能随之写错。
- 修复方向：加请求序号（seq）丢弃过期响应。

**N-12｜ReaderView.vue：零章节书籍进入错误页而非空态（严重度：中）**
- 问题：`loadAll` 中 `loadChapter(target!, true)`，书籍无章节时 target 为 null，URL 拼成 `/chapters/null` 触发 404 走 loadError 分支。
- 影响：新上传/解析失败的书显示刺眼错误态，无引导。
- 修复方向：target 为空时渲染空态提示。

**N-13｜ReaderView.vue：onBeforeUnmount 未 abortChat（严重度：中）**
- 与 N-3 同源，视图侧遗漏点。

**N-14｜ReaderView.vue：页图预加载边界（严重度：低）**
- 问题：预加载条件 `pageIndex && pageIndex > 1` 在 0/1 基数边界行为含糊；末页时 `pageIndex < totalCount` 的预取可能请求不存在的页。
- 说明：待与后端 page_index 基数语义核对。
- 修复方向：统一基数约定并做边界钳制。

**N-15｜ReaderView.vue：段落笔记按钮键盘不可达（a11y）（严重度：中）**
- 问题：`.para-actions` 四个按钮 `v-show="hoverPara === i"` 仅 mouseenter 显示，纯键盘用户无法触达高亮/提问/笔记/不理解功能。
- 修复方向：focus-within 同样显示，或提供常显的段落选中入口。

**N-16｜RagView.vue：总结任务不进任务中心 + refresh 无 catch（严重度：均为中）**
- 问题一：`runSummarize` 未调 `notifyTaskSubmitted()`，与全站「提交后台任务→任务中心轮询」的约定不一致，用户在任务中心看不到总结任务。
- 问题二：`refresh()` 无 try/catch，`onMounted(refresh)` 失败即 unhandled rejection 且页面无任何提示。
- 修复方向：补 notify；refresh 加 catch + 错误提示。

**N-17｜RagDetailView.vue：bookId 无 NaN 防护（严重度：中）**
- 问题：`const bookId = Number(route.params.bookId)`，访问 `/rag/abc` 时渲染「书籍 #NaN」并对后端发起 NaN 请求。
- 修复方向：路由参数校验或 NaN 时跳回列表。

**N-18｜ProfileView.vue：刷新无兜底 + 大量 any 穿透（严重度：均为中）**
- 问题一：`refresh()` 中 Promise.all 三接口任一失败整个页面数据为空且无提示（无 try/catch）。
- 问题二：`ProfileLayer = [key:string]: unknown`，模板与 computed 中大量 `as any[]` 后直接访问 `r.key_points.length`、`profiles.hot.current_title` 等嵌套字段，后端结构微调即运行时崩溃，TS 类型形同虚设。
- 修复方向：Promise.allSettled + 逐块降级；为三层画像定义具体接口并做边界空值保护。

**N-19｜GraphView.vue / SettingsView.vue：waitForTask 不可取消（严重度：中）**
- 问题：`utils/task.ts` 的 `waitForTask` 是纯循环，无 AbortSignal；等待期间离开页面后轮询最长持续到超时（默认 10 分钟，设置页连接测试为 120s）。
- 修复方向：支持 AbortSignal 参数，调用方绑定 onScopeDispose。

**N-20｜HomeView.vue：可点击卡片无可访问性属性（a11y）（严重度：中）**
- 问题：book-card / book-cover / recent-item 等可点击 div 无 role/tabindex/键盘事件；book-actions 仅 hover 显示（opacity 0）。
- 修复方向：关键操作提供 button 语义或 `role="button"` + keydown。

**N-21｜SettingsView.vue：getField/setField 用 `(form as any)[key]` 擦除类型（严重度：低）**
- 修复方向：`key: keyof AiSettings` 泛型约束。

### 3.3 components

**N-22｜MdRender.vue：markdown-it 每实例新建 + KaTeX auto-render 每次异步 import（严重度：高）**
- 问题：`new MarkdownIt(...)` 写在 setup 内，每个组件实例一份；阅读页每段一个 MdRender，长章节可达数百个实例；且每次 html 变化都执行 `await import('katex/dist/contrib/auto-render.mjs')`。这是「KaTeX/markdown-it 重复初始化」排查项的确认结论。
- 触发条件：打开长章节。
- 影响：初始化开销叠加、GC 压力、首段渲染被异步 import 阻塞。
- 修复方向：markdown-it 实例提升为模块级单例；auto-render 模块级缓存 promise（参考 `utils/graphLabel.ts` 的 `ensureKatex` 模式，该项目内已有正确范式）。

**N-23｜MdRender.vue：linkify 生成的链接无 target（严重度：低）**
- 问题：正文中的链接点击后直接在当前标签页跳转，离开 SPA 丢失阅读状态。
- 修复方向：renderer 覆写补 `target="_blank" rel="noopener"`。

**N-24｜BookmarkDrawer.vue：错误被静默吞掉 + para_pos 恒为 null（严重度：中 / 低）**
- 问题一：`edit()`/`remove()` 的 catch 同时吞掉「用户取消 ElMessageBox」和「API 失败」，书签更新/删除失败无任何反馈。
- 问题二：`addCurrent` 恒传 `para_pos: null`，而 `jumpToBookmark` 支持 para_pos——书签永远只能跳章节不能回到原段落。
- 修复方向：区分 cancel 与 error；添加书签时带上当前段落位置。

**N-25｜TaskCenter.vue：历史终态任务每次挂载重复弹出（严重度：中）**
- 问题：`pollOnce` 把后端返回的全部终态任务（保留 7 天）pushRecent，应用每次挂载都会把数天前的已完成任务弹进「最近完成」浮窗。
- 影响：用户每次打开应用都被旧任务通知打扰，通知失去时效意义。
- 修复方向：按 session 或时间窗过滤，或记录已展示的 task id（localStorage）。

**N-26｜MindMapPanel.vue（正例，不登记问题）**：ECharts init/dispose/ResizeObserver/resize 处理完整规范，可作为 GraphView 重构参照。

### 3.4 api / 全局架构

**N-27｜api/client.ts：错误归一化覆盖不完整 + 无请求取消支持（严重度：中）**
- 问题：归一化仅覆盖 axios 错误路径（`err.response?.data?.detail || err.message`），成功响应不校验结构；axios 实例未暴露 AbortController 取消能力（N-11 竞态的根因之一）。SSE 走原生 fetch 完全绕过拦截器，错误格式与主链路不一致。
- 修复方向：统一请求工厂支持 signal；SSE 错误也走归一化。

**N-28｜App.vue：`<router-view :key="String(route.fullPath)">` 全量重挂载（严重度：中，架构权衡点）**
- 问题：query 变化也触发整页重挂载；该策略规避了跨书状态残留，但同时使 keep-alive、滚动恢复、组件级缓存全部不可用，是多个体验问题的结构性根因。
- 修复方向：key 收窄为路由 path 或 bookId，状态清理改为显式 reset。

**N-29｜stores/book.ts：recentBooks 是方法而非 computed（严重度：低）**
- 问题：模板中每次调用都重复计算排序/过滤；books 数组直接暴露可写（视图直改问题已登记，此处登记计算属性缺失）。

### 3.5 utils

**N-30｜graphLabel.ts：加载失败永久缓存，无重试（严重度：低）**
- 问题：`ensureMathJax` 失败时 `mathJaxApi=null` 但 `mathJaxReady` 已 resolve，后续调用不会再尝试加载；markdown-it/DOMPurify 同理。一次偶发 chunk 加载失败会导致图谱公式标签本会话内永久降级为纯文本。`formulaCache` 为无上限 Map（量级受节点数约束，影响小）。
- 修复方向：失败时重置 ready promise 允许重试。

**N-31｜utils/task.ts：waitForTask 无取消机制**（见 N-19，根因在此文件）。

**N-32｜content.ts：splitCache 非真 LRU（严重度：低）**
- 问题：命中不更新顺序，淘汰按插入序；影响极小，仅缓存效率。

### 3.6 构建与依赖

**N-33｜Element Plus 全量引入（严重度：低）**
- 问题：main.ts 全量注册，vendor-element chunk 体积大；manualChunks 未包含 mathjax-full（实际被 graphLabel.ts 动态 import，属按需加载，合理，但首次打开含公式图谱会额外拉取 MB 级 chunk，值得在使用手册说明）。
- 修复方向：unplugin-vue-components 按需引入。

**N-34｜构建配置总体健康（正例，不登记问题）**：tsconfig `strict: true`、`build = vue-tsc --noEmit && vite build`、manualChunks 四包拆分、vite 6 + vue-tsc 2 版本无已知兼容问题；依赖版本（vue 3.5 / element-plus 2.9 / echarts 5.6 / katex 0.16 / dompurify 3.2）均无已知高危 CVE。`historyReplaceDefuse.ts` 对 Chromium 最小化缺陷的规避有详尽注释，设计可靠。

## 四、可拓展性分析

> 合并后端与前端两份调研的可拓展性结论，按扩展场景组织。后端文件路径相对于 `backend/app/`，前端相对于 `frontend/src/`。

### 4.1 新增书籍格式（HTML/DOCX）— 成本：中（后端）
- 涉及文件：`parsers/`（新增 parser）、`parsers/__init__.py` parse_book 的 if/elif 分发与 SUPPORTED 白名单、`api/routes/books.py` 上传后缀校验、`import_service.py`、`media_service.py`/`book_pages.py`（页图逻辑 PDF 专属，新格式需声明「是否可出页图」）。
- 设计评价：**无 Parser 基类/能力接口**，只有共享数据结构 ParsedBook；「是否扫描版/有无页图/封面来源」等能力差异靠调用方 if format 判断，散落在 5+ 处。
- 建议：定义 `BaseParser`（parse / supports_pages / extract_cover）+ 注册表，新格式只新增一个文件 + 一行注册。

### 4.2 新增 AI 接口格式 — 成本：中偏高（后端）
- 涉及文件：`ai/client.py` 需同步改 `_build_body`、`_extract_reply`、`_extract_delta`、`_PATH_SUFFIXES`、`_AUTO_PATHS` 5 处分发；`repositories/settings.py` 的 AI_OVERRIDE_KEYS/类型集合；`.env.example`。
- 设计评价：三种格式（responses/chat/anthropic）以 if mode 内联于单类，无接口抽象；**vision 与 text 配置分离良好**（独立 vision_* 全套 + 独立限流池），但 `vision_client_kwargs` 硬编码强制 chat 模式（SiliconFlow 假设），换 vision 提供商需改仓储层；`ai/factory.py` 仅封装 text 客户端，vision/selector 客户端在各自调用点手工组装 kwargs，无统一工厂。
- 建议：把「接口格式」抽为策略对象（build_request/parse_reply/parse_delta 三方法），工厂统一产出 text/vision/selector 三种客户端。

### 4.3 新增 AI 交互模式（总结/问答之外）— 成本：中-高（前端）
- 涉及文件：`ReaderChatPanel.vue`（入口与消息渲染）、`composables/useReaderAi.ts`（请求分支与流式状态机）、`api/chat.ts`（SSE 参数）、`types.ts`、后端对应接口。
- 设计评价：无「AI 交互模式」抽象层，模式差异散布在 UI 与 composable 两处 if 分支；但 SSE 流式基础设施（fetch 流解析、节流 flush、公式未闭合延迟、stream_key 落库补偿）是通用的，可复用。
- 建议：抽 `useAiStream(mode, payload)` 通用流式层，模式只定义参数与渲染器。

### 4.4 新功能扩展点 — 成本均低~中（后端）
- **任务类型**（中）：`tasks/__init__.py` `_quota_for` 只认 text/vision/render 三类，新类型落 generic 无配额管控；任务注册靠各路由手工 submit，无注册表。新增类型需改配额映射 + 提交点 + 前端任务中心文案。
- **图谱边类型**（低）：BookRelation.relation_type / KpRelation.relation_type 均为自由字符串，新增类型只需在生成逻辑加分支 + 前端图例；代价是无枚举约束，类型一致性靠约定。
- **画像维度**（中）：UserProfile(layer, dimension) 表结构自由，但读写按维度硬编码函数（get_hot/get_warm/get_cold + migrate 内联逻辑），新维度需新增读写函数并接入归档迁移。
- **chat 模式**（低）：mode 为自由字符串，会话键 `book:{id}:{mode}` 自动分池；但 `CACHEABLE_MODES` 硬编码（新模式默认不享受 LLM 缓存）、prompt 需加进 `ai/prompts/chat.py`。

### 4.5 新增路由页面 — 成本：低-中（前端）
- 涉及文件：`router/index.ts`、`App.vue`（导航项硬编码于侧边栏）、新建 view、按需新建 `api/*.ts`、`types.ts` 补类型。
- 设计评价：路由/导航/类型三步机械；但无页面级约定骨架——loading/error/空态样板每个新页自写（HomeView/RagView/ProfileView 各一套），新页会复制已知错误样板问题。
- 建议：接入成本低但缺「页面模板」；建议沉淀 usePageData(fetcher) 泛型 composable 统一 loading/error/retry。

### 4.6 组件复用（前端）
- 现状：`components/` 8 个组件全部是阅读器领域专用件；真正的通用 UI 模式反复手写在 views 里——统计卡片（HomeView stat-card vs ProfileView stat-card）、空态块（layer-empty / empty-tip / el-empty 三种写法并存）、键值网格（kv-item）、面板头（panel-head / layer-head）。
- 成本：提取单项低，整体整理中。
- 建议：提取 EmptyState、StatCard、SectionPanel 三个基础组件；MdRender 是唯一已成熟的通用组件（但需先修 N-22）。

### 4.7 主题与国际化（前端）
- 主题：`styles/theme.css` 集中定义 CSS 变量，暗色仅跟随 `prefers-color-scheme`（无手动切换开关）。**暗色模式完善成本：中**——变量层已就绪，但 Element Plus 组件未接 `html.dark` 类名体系，且 `utils/graphEdges.ts` 等处存在硬编码 rgba 颜色字面量、部分 scoped 样式硬编码 `#fff`，需逐项替换。
- i18n：**改造成本：高**。无 vue-i18n、无任何词条文件；全部文案硬编码中文，分布于 7 个 views + 8 个 components 的模板、composables/api 层错误提示、ElMessage/ElMessageBox 调用参数、SettingsView 两张字段配置表（label/tip 全中文）；按代码体量估算约 **600~900 条独立文案**，另需处理日期/数字格式与 emoji 图标。短期不建议启动。

### 4.8 图表库扩展（前端）
- 耦合度：高。ECharts option 在 GraphView（712 行）与 MindMapPanel 内联拼装（option 拼装本身是既有已知问题 A-2，此处评估耦合面）；已抽离的部分：`graphEdges.ts`（边颜色/端点）、`graphLabel.ts`（MathJax 公式标签 → rich 文本），这两个纯函数层是替换/升级时的主要可复用资产。
- 成本：**ECharts 5 内升级低；替换为其他库高**（force/tree 布局、rich label、tooltip formatter 均需重写，graphLabel 的 SVG 图片嵌入方案与 ECharts rich 深度绑定）。

### 4.9 架构瓶颈（后端）
- **单用户假设渗透深（多用户改造成本：高）**：UserProfile/Setting/tasks/llm_caches/画像/会话键均无 user_id 维度；rag_router 进程内缓存、graph_clusters.json 落盘缓存均为全局单份。粗估涉及全部 7 张核心表加列 + 全部仓储/会话键加过滤，属重构级改造。
- **SQLite 上限**：单写者 + 30s busy timeout 已被问题 5（分钟级写事务）实际击穿；WAL 下读并发良好。书量千册级内无忧，写密集场景（多任务并行图谱重建）是第一个撞墙点。
- **仓储层覆盖不全**：search（直拼 SQL）、graph 反馈、settings 客户端构建、profile 读写等多处绕过仓储直连 ORM/SessionLocal（部分已登记）。对未来替换数据层（如 PostgreSQL）而言，这些绕过点是隐性改造成本。

### 4.10 测试友好度

**后端**：
- 现有 27 个测试文件覆盖了 graph（4 个）、assets、chat、profile、reading、rag_router、vision、tasks、perf 等主要面。
- **零覆盖薄弱区**（按风险排序）：
  1. **导入链路**（import_service + import-background）——全系统最复杂链路竟无任何测试；
  2. **search_service**（FTS5 + LIKE 回退双路径）；
  3. recommendation_service、citations、rag_input（纯函数，最容易补）。
- 依赖注入困难点：settings 全局单例、build_client 直接读 DB、线程池/信号量模块级全局，测试需大量 monkeypatch（conftest 已有 tmp 目录+临时库基建，可复用）。

**前端**：
- 现状：6 个测试文件（vitest，`npm test`）**全部位于 utils 纯函数层**——progress、content（splitBlocks）、math（公式归一化）、graphLabel、graphEdges、annotations、text，覆盖质量较高（含边界与非法输入用例）。
- 缺口：**composables / stores / components / views / api 层测试为 0**。无测试保护的关键逻辑：SSE 流解析与去重（N-4）、cachedSplitBlocks 缓存（LRU 淘汰未测）、waitForTask 超时路径、useReaderPageCache 可见性切换（N-1 若有测试早已暴露）、store 排序逻辑。无 coverage 配置、无组件测试环境（jsdom）。
- 建议优先级：先给 composables 补单测（纯逻辑可测性尚可），组件测试可缓。
