# 多语言重构评估

- **日期**：2026-08-05
- **状态**：调研结论，供决策参考
- **关联文档**：[技术栈规范.md §6 ADR-010](../技术栈规范.md)、[docs/性能优化路径.md](./性能优化路径.md)

## 结论速览

- 逐环节核查（按 300 本书规模估算）表明：交互主链路延迟 100% 来自 LLM 网络与 DB/文件 IO，纯 Python 计算不在任何同步请求路径上。
- 纯 Python 热点最坏情形为「秒~分钟级一次性后台耗时」，远低于 ADR-010 自设的「profile >30s」触发线，当前连 numpy 都不需要。
- Rust/Cython/Go 重写/C++/WASM 全部候选均不通过收益/成本检验，且直接冲突 ADR-010。
- **总体结论：不需要语言重构，维持 ADR-010**；剩余优化预算投入纯 Python/TS 项（倒排索引、批量预载、缓存策略、前端 md 单例）。

## 调研对象与约束

- 项目：`e:\python\LLMnotebook`（FastAPI 后端 + Vue3 前端 + SQLite，本地单用户、Windows、无 GPU；当前库约 12 本书、`llmnotebook.db` 约 1.5MB，目标数百本）
- 环境实测：Python 3.12.13、PyMuPDF 1.28.0（底层 MuPDF 为 C 实现）
- 约束原文（`技术栈规范.md` §6，ADR-010，v1.61）：

## 2. 候选语言/技术逐一评估

### 2.1 Rust + PyO3 / maturin 原生扩展
- **适用环节**：关键词冷抽取、`_pair_score` O(N²)、聚类贪心。
- **预期收益**：10~50x 计算加速。但收益折算到墙钟：把 1~5s 的跨书评分降到 <0.5s、把 3~10min 的一次性全量冷抽取降到 <1min——均为后台任务，不改善任何可感知的交互延迟。
- **集成成本**：高。Windows MSVC 工具链 + maturin 构建链、wheel 分发、与 Poetry/venv 流程整合、测试矩阵翻倍。
- **维护成本**：高。双语言代码库，项目现有的「使用手册逐函数登记 + 耦合审查」收尾规范（技术栈规范 §5）对 Rust 模块难以执行。
- **ADR-010 冲突**：直接冲突（明确列出 Rust）。

### 2.2 Cython / C 扩展
- 适用与收益同 2.1，开发体验更差（无类型安全、构建更繁琐），收益/成本比低于 PyO3。**不推荐**，直接冲突 ADR-010。

### 2.3 Go / Rust 重写后端服务（替换 FastAPI）
- **适用环节**：整体替换。但后端延迟构成是：LLM 网络（主导）、SQLite C 层、文件 IO、pymupdf C 层——FastAPI/Python 框架本身开销在每请求 <1ms 量级，重写后用户感知为零。
- **预期收益**：≈0（交互式延迟不变），内存略降（百 MB 级→几十 MB 级，桌面无感）。
- **成本**：重写全部 ORM/迁移（SQLAlchemy+Alembic）、28 个测试文件、189+ 项用例、全部文档体系。数周~数月级。
- **ADR-010 冲突**：最严重。**不推荐**。

### 2.4 C++（PDF 渲染链）
- PyMuPDF 即 MuPDF（C）的 Python 绑定，`get_pixmap`/JPEG 编码均在 C 层；Python 壳开销 <5%（`parsers/pdf.py` 仅做 open/循环/保存路径）。重写无收益，还失去 pymupdf 的维护红利。**不推荐**。

### 2.5 WASM 前端（markdown/公式渲染）
- markdown-it/DOMPurify/KaTeX 单章渲染在百 ms 级，真正开销是「每 block 一个 MdRender 实例」的组件架构（200 个 MarkdownIt 实例 + 200 次 KaTeX 遍历）。WASM markdown 引擎（如 pulldown-cmark-wasm）只加速解析一环，KaTeX DOM 输出与消毒仍须留在 JS，且引入二进制体积与调试成本。正确解法是纯 TS 改造（共享 md 单例、整章一次 render、公式批处理）。**不推荐**。

### 2.6 Python 内部优化（对照组）
- **numpy 向量化**：ADR-010 明文允许的退路。但按上表估算，300 书跨书评分 1~5s、聚类 1~3s，远未达到 ADR-010 设定的「profile >30s」触发线——**当前连 numpy 都不需要**。且注意 `_pair_score` 是稀疏短向量（80 维）点积，numpy 的启动开销可能抵消收益；真正值得做的是算法层：共享词倒排索引（性能优化路径已列，「数百本时启用」）+ `_note_weight` 笔记关键词一次性批量预载（当前逐对 2 次 DB 查询是唯一真正的 O(N²) 放大源）。
- **lru_cache / 缓存**：已系统性落地（关键词内容寻址缓存、聚类群体签名落盘缓存、`_target_width_cached`、LLM 结果表缓存、前端 `cachedSplitBlocks`）。剩余小项：关键词缓存改 LRU 代替「溢出整体清空」（避免 300 书时命中率震荡）。
- **批量预取/并发**：`render_pdf_pages` 与 `enrich_pairs_with_llm` 已并发化（决策 35）。
- **收益对比**：纯 Python 算法改进可拿走剩余热点的 80%+ 空间，成本为天级，零 ADR 冲突；Rust 扩展拿走同样空间，成本为周级且破坏约束。

### 2.7 SQLite 层优化
- 已做：WAL、外键/热点索引（`_ensure_indexes`）、PRAGMA（synchronous=NORMAL / 20MB cache / 256MB mmap）、FTS5 trigram + 触发器同步。剩余空间：短词 LIKE 回退的全表扫（可接受）、`ANALYZE` 周期化、FTS 索引体积治理——均属数据层微调，与语言无关，细节留给存储调研。

## 4. 结论与建议

### 4.1 总体结论：不需要语言重构，建议维持 ADR-010

证据链：
1. **交互链路零热点**：阅读/问答主路径的延迟 100% 来自 LLM 网络与 DB/文件 IO，纯 Python 计算不在任何同步请求路径上（图谱懒构建 + 增量 + 落盘缓存，见 `cross_book.py::incremental_cross_book_graph`、`clustering.py::assign_clusters`）。
2. **热点量级低于触发线**：300 书规模下最坏估算——跨书评分 1~5s、聚类 1~3s、关键词冷抽取为一次性后台分钟级；均未达到 ADR-010 自设的「>30s 再考虑 numpy」阈值，且 LLM 打分（15~60s）才是图谱重建的主导耗时，而它是网络问题。
3. **C 层已覆盖重计算**：PDF 渲染（MuPDF）、全文检索（FTS5）、存储（SQLite）全部在 C/C++ 层，Python 只是胶水。
4. **重构的隐性成本被项目规范放大**：使用手册逐函数登记、耦合审查、pytest 基线（189 项）等收尾体系是纯 Python/TS 设计的，引入第二语言会使该质量体系失效。

### 4.2 「维持约束」视角（推荐采纳）
ADR-010 的判断在本轮逐环节复核后依然成立，且比 v1.61 时更稳固（此后已落地：上传流式写盘、关键词/聚类/LLM 三层缓存、FTS5、索引、PRAGMA、渲染与打分并发化）。建议：保持 ADR-010 原文不动，把剩余优化预算投入纯 Python/TS 项：
- P1：`_note_weight` 笔记关键词批量预载（消除唯一真正的 O(N²) DB 查询放大）；
- P1：前端 MdRender 共享 markdown-it 单例 + 整章批处理渲染（解决 200 实例问题）；
- P2：关键词缓存改 LRU 淘汰；共享词倒排索引按性能优化路径约定在书量接近数百本时启用；
- P3：`applyHighlights` 笔记多时按章内 quote 建索引（可选）。

### 4.3 「有限破例」视角（仅作压力测试，不构成当前建议）
若必须寻找破例点，唯一勉强成立的是：把跨书评分+聚类封装为 Rust 扩展。但量化后其收益（把 1~5s 后台任务压到亚秒）与成本（工具链/分发/双语言维护/规范失效）严重不成比例，且同样的收益可用倒排索引+numpy 在约束内达成。**结论：即便在有限破例视角下，也没有一个候选通过收益/成本检验。** 唯一被 ADR-010 预留的「外来代码」通道是未来本地向量检索（faiss/sqlite-vec 的 Python 绑定），那属于 C++ 库绑定而非语言重构，与本任务结论不冲突。

### 4.4 触发重新评估的条件（建议登记为 ADR-010 复审门槛）
出现以下任一情形时，先做 profile 实测，再复审 ADR-010：
1. 书量达到 **500 本以上**，且全量图谱重建（剔除 LLM 打分耗时后）实测 **>60s**，且倒排索引/numpy 向量化已实施仍不达标；
2. 图谱相关接口进入**同步交互路径**（不再后台懒构建）且用户可感知卡顿 >3s；
3. 关键词缓存整体清空导致的重算在实际使用中频繁发生（>每日一次）且 LRU 改造后仍不缓解；
4. 引入本地 embedding/向量检索后，向量计算（非检索，检索有 C 绑定）成为新热点且 profile 占比 >30%；
5. 单章正文规模增长到 MB 级（如整书单章导入），前端渲染实测 >2s 且 TS 侧批处理/虚拟滚动手段已用尽（届时评估 WASM 渲染，也须先过 ADR 评审）。
