# 联动沉淀优化方案

- **日期**：2026-08-12
- **状态**：方案已固化，按 L0→L1→L2 分轮实施（每轮修改后审查+测试）
- **关联文档**：docs/待办清单.md（登记）、需求文档.md §3.4.7/§3.4.9、backend/app/services/graph_sync.py、backend/app/services/graph/clustering.py

## 0. 背景与目标

- 联动沉淀（`POST /api/graph/sync` → `sync_assets_for_relations`）当前问题：
  1. 每条活跃边两个方向各一次 LLM 调用（2E 次），同一本书被 k 条边关联时重复调用，整本资产反复重写；
  2. `post_classify_book` 在每次 LLM 更新后触发，且每次重新读全部已分类书资产（O(M·C)），E 次累计 O(E·M·C)；
  3. 无幂等指纹：重复执行 `/sync` 会再次消耗全部 token；
  4. LLM 调用串行，无并发。
- 目标：调用次数 2E→U（受影响书数）、重跑零消耗、post_classify 移出边循环、并发可控（feature flag）。
- 原则：每轮修改前确定方案；修改后审查；疑似问题先测试定位再改；代码符合现有规范（仓储/服务分层、docstring、类型标注）；为后续桌面/移动端移植与 LLM 并发改造预留冗余（并发只做网络 IO、落盘回主线程）。

## 1. 现状链路（代码定位）

- 入口：`api/routes/graph.py:85` `POST /api/graph/sync` → `graph/tasks.py:53` `sync_assets_task` → `graph_sync.py` `sync_assets_for_relations`
- 逐边处理：`link_relation_stubs`（本地存根，O(1) 幂等）→ `_llm_link_update`（每边两方向 LLM 调用 + 每次成功后 `post_classify_book`）
- `post_classify_book`（clustering.py:206）：tag/文件夹硬约束 → 后验关键词校验（T_POST=3）→ 迁移 → 维持/新名；`_cluster_repr` 每次遍历 others（O(M·C)）
- `merge_and_rename_clusters`（clustering.py:284）：簇合并（T_MERGE=5）+ 重命名，只处理 classify_source=post

## 2. 方案分层

### L0 · 本地计算层（低风险，不动 LLM 行为）

1. **ClusterIndex 预计算**：在 `sync_assets_for_relations` 入口一次性构建 `{cluster_name: set(后验关键词)}`（读 M 本书资产一次），`post_classify_book` 增加可选 `index` 参数复用 → 单次 post_classify 从 O(M·C) 降到 O(C)。
2. **post_classify 移出边循环**：收集受影响 book_id 集合 U，全部 LLM/存根更新结束后对 U 逐本执行一次 post_classify；`merge_and_rename_clusters` 最后统一跑一次。
3. **commit 隔离**：LLM 更新成功后先 commit 落库，post_classify 失败只回滚分类不丢资产（修复当前 `db.rollback()` 回滚已成功更新的问题）。

### L1 · LLM 调用层（中风险，收益最大）

4. **按书聚合多边（multi-link）**：把「每边 2 次调用」改成「每本书 1 次调用」——收集该书本轮全部关联边（other 标题、relation_type、strength、reasons），`rag_link.py` 新增 `build_multi_link_user_prompt`（单边版保留兼容），一次输出整本合并资产。上限保护：每本书单轮最多聚合 K=8 条边（按 strength 取 top-K），其余边只补本地存根。
5. **幂等指纹**：每本书记录「最近一次联动指纹」= 本轮边集合哈希（relation_id + strength + direction 排序后哈希），存资产元数据（`rag.linked_sync_fingerprint`）。重跑 `/sync` 指纹一致直接跳过 LLM 与版本递增；边有增改才重新联动（天然增量）。
6. **增量剪枝**：`sync_assets_for_relations` 已有 `relation_ids` 参数，前端/任务默认只传「上次同步后新增/变更的边」，全量同步改为显式 `force` 参数。

### L2 · 并发层（中高风险，最后做，feature flag 默认关）

7. **并发 LLM 请求**：复用 `settings.ai_concurrency`（0=不限制）信号量 + `ThreadPoolExecutor`（参考 `llm_score.py:113` 既有模式）。关键约束：**并发只做网络请求，不碰 db**——拆成「构造 prompt（主线程）→ 并发 chat（子线程，只读入参）→ 主线程解析 JSON + upsert 落盘」。
8. **进度细化**：任务进度按「书级」上报（每本完成更新百分比）。

## 3. 并发红线（所有轮次必须遵守）

1. 子线程只做网络 IO，不触碰主线程 Session 与 ORM 对象；
2. 落盘一律回主线程串行、短事务、每书独立 commit 边界；
3. sync 内部不提交嵌套任务、不申请任务配额，只受 `ai_concurrency` 信号量；
4. 资产写前乐观校验版本，冲突跳过并上报；
5. 先落地 L1 幂等指纹再开 L2 并发（指纹同时解决重跑与重启中断）；
6. 并发默认关、feature flag 开，可随时回退单边串行模式。

## 3.5 L1 实施细节（v1.1 定稿，2026-08-12）

### 3.5.1 聚合模型
- 以「本轮 sync 处理的关联边集合」为单位：`relations = list_active_relations(db, relation_ids)`。
- 按书聚合：`by_book: dict[int, list[LinkEdge]]`，`LinkEdge = (other_title, relation_desc, reasons, strength, rel_id, direction)`。
- 每本书的边按 `strength` 降序，截断到 `MAX_LINKS_PER_BOOK = 8`（graph_sync.py 常量，可调参）；被截断的边只补本地存根（linked_books），不参与 LLM 上下文。
- 每本书一次 LLM 调用（multi-link 提示词），输出整本合并资产（与原单边版同构，兼容回退）。

### 3.5.2 幂等指纹
- 指纹 = 该书本轮边集合的稳定哈希：`sha256(json.dumps(sorted([(rel_id, round(strength,1), direction)]), sort_keys=True))[:16]`。
- 存储：`rag["linked_sync_fingerprint"]`（与 LLM 输出同一批 upsert_asset 写入；指纹字段不影响 `_posterior_keywords`/`linked_books` 语义）。
- 命中规则：旧 rag 指纹 == 本轮指纹 且未 force → 跳过 LLM（不计入 affected、不 bump 版本）；否则正常联动。
- 语义：任一边增删/强度变化/方向变化 → 指纹变 → 重新联动；重跑 /sync 零消耗。

### 3.5.3 force 与增量
- `sync_assets_for_relations(db, relation_ids=None, *, use_llm=None, force=False)`；`force=True` 忽略指纹强制联动。
- 增量：调用方传 `relation_ids`（新增/变更的边）即天然增量；任务/路由层暂不暴露 force（预留参数，后续需要时接入）。

### 3.5.4 返回统计
- `{"stubs", "llm_updated", "llm_skipped"}`：`llm_skipped` = 指纹命中跳过的书数（验收与观测用）。

### 3.5.5 兼容与回退
- `build_link_user_prompt`（单边版）保留；multi 版 `build_multi_link_user_prompt` 在 links 长度为 1 时退化为单边语义。
- L1 默认启用聚合；如质量异常可回退：把 `_llm_link_update` 改为逐边调用（保留旧函数签名路径的文档说明）。

## 3.6 L2 实施细节（v1.2 定稿，2026-08-12）

### 3.6.1 配置与开关
- 新增 `GRAPH_SYNC_CONCURRENCY`（settings.graph_sync_concurrency，默认 `1`）：
  - `1` = 串行（默认，即「并发默认关」，行为与 L1 完全一致）；
  - `0` = 不限制（worker 数 = min(受影响书数, 8)）；
  - `N>1` = 并发上限 N（cap 8，与 llm_score 上限一致）。
- **配置来源（v1.3）**：`.env` + 设置页运行时覆盖——`repositories/settings.py` 将
  `graph_sync_concurrency` 纳入 `AI_OVERRIDE_KEYS`/`_INT_KEYS`，`load_ai_overrides(db)`
  优先返回 DB 覆盖（设置页保存），未覆盖回退 `.env`；设置页「并发」分区可填 0~8。
- 并发仍受 `ai_concurrency` 信号量约束（client.chat 内部统一限流，决策 35 红线 3）。
- **0=不限制死代码修复（v1.3）**：原 `if n <= 1: return 1` 拦截了 `0`，导致 `0` 永不生效；
  已改为先判 `n == 0 → min(max(total,1),8)`，再判 `n <= 1 → return 1`。

### 3.6.6 真实 API 冒烟实测（v1.3，2026-08-12）
- 环境：真实库副本（临时目录，跑完即弃），6 本受影响书（11 条活跃边≥50），
  deepseek-v4-flash（thinking=enabled），AI_CONCURRENCY=8；每个档位从干净副本重跑（指纹不命中）。
- 结果：

| 并发 | 耗时(s) | LLM 更新书数 | 备注 |
|---|---|---|---|
| 1（串行） | 931 | 6/6 | 基准（每书约 155s） |
| 4 | 311 | 6/6 | **甜点**：约 3.0x 加速，全部成功 |
| 8 | 188 | 4/6 | 约 5.0x 加速，但 2 本失败（上游限流/超时，按书回滚不阻塞） |

- 结论：默认保持 `1`（安全基线）；设置页推荐值 **4**（与 AI_CONCURRENCY 实测甜点一致）；
  `0`/`8` 提速最多但存在上游限流风险，仅建议在容错要求低的批量场景使用。

### 3.6.2 三段式执行（红线 1/2 落地）
- **主线程准备**：逐书（id 升序，确定性）指纹判定 + 读旧资产 + 构造 multi-link 提示词（只读 DB）；
- **并发 chat**：仅网络 IO，不触碰主线程 Session/ORM；共享一个 `build_client` 构建的客户端（LLMClient 每次调用无状态、线程安全）；每书 chat 独立捕获异常（失败返回异常对象，不中断其它书）；
- **主线程落盘**：按序解析 JSON + 构造 RAG/Skill + `upsert_asset`（短事务、每书独立 commit 边界）；单书失败 `db.rollback()` 后继续。
- 串行（workers=1）走同一三段代码路径，保证「并发开关」只影响调度、不影响语义。

### 3.6.3 进度回调
- `sync_assets_for_relations(..., on_progress: Callable[[int, int], None] | None = None)`；
- LLM 落盘阶段每完成一本书回调 `(done, total)`，total=落盘书数（指纹跳过瞬时完成不计入）；
- 任务层 `sync_assets_task` 映射到 20%→70% 窗口：`20 + 50 * done / total`，消息「LLM 联动 done/total」。

### 3.6.4 重构与兼容
- `_llm_link_update` 拆分为 `_prepare_link_update`（返回 None=指纹命中跳过；否则返回
  (book, old_rag, old_skill, fingerprint, messages)）与 `_apply_link_update`（解析+落盘）；
- 对外签名 `sync_assets_for_relations(db, relation_ids=None, *, use_llm=None, force=False, on_progress=None)` 向后兼容；
- 返回结构不变：`{"stubs", "llm_updated", "llm_skipped"}`。

### 3.6.5 测试（非视觉 e2e：API 级断言）
- 并发调用次数与串行一致（每书一次）；结果一致；
- 并发峰值验证（fake client 内记录同时在飞请求数 ≥ 2）；
- 单书 chat 失败隔离（其它书照常落盘）；
- 进度回调序列 (1,total)…(total,total)；
- 全量 pytest + ruff 全绿。

## 4. 验收标准

- E=500 活跃边时 LLM 阶段调用次数 ≤ U（受影响书数，聚合后）；
- 重复执行 `/sync`（指纹一致）不重复消耗 token（0 次 LLM 调用）；
- post_classify 只对受影响书执行一次，累计耗时可忽略；
- L0/L1 不改变 LLM 输出语义（回归测试：单边模式与现有一致）；
- 现有 pytest（291+）与 ruff 全绿；e2e 若涉及使用非视觉方案（API 级断言，不用浏览器截图）。

## 4.5 审查记录（2026-08-12 L1/L2 轮）

- **L0 语义回归（测试定位→修复）**：共享簇索引初版为「簇→关键词并集」，批量路径下把被归类书自身
  关键词计入当前簇重叠（自匹配），压制簇迁移（无索引路径会迁移、共享索引路径滞留）。新增回归测试
  `test_post_classify_shared_index_excludes_self` 复现后，改为**按书粒度** `{cluster: [每本书关键词集合]}`，
  计算当前簇代表特征时跳过本书自身集合——语义与逐本现构建完全一致（集合相等跳过对并集无影响）。
- **测试确定性修复**：直接改 `cluster_name/classify_source` 而不同步 `classify_version` 会被后续导入的
  `assign_clusters` 判定 post 失效重置为 pre；测试夹具改为同步 `classify_version = 资产版本`（与
  `post_classify_book` 语义一致）。
- **红线 4 说明**：资产写前乐观版本校验未单独实现——同书并发写由 `_asset_write_lock`（per-book 锁）串行，
  同型任务并发由任务防重（submit_dedupe）拦截，与全局资产写路径一致；指纹为 sync 自身幂等层。
- **L2 并发验证**（非视觉，API 级断言）：峰值并发 ≥2、调用次数与串行一致、失败按书隔离、进度序列
  (1,total)…(total,total)；全量 325 pytest + ruff 全绿。
- **v1.3 设置页化**：`GRAPH_SYNC_CONCURRENCY` 增加运行时 DB 覆盖（设置页「并发」分区），
  `_sync_llm_workers` 消费 `load_ai_overrides(db)`；修复 0=不限制被 `n<=1` 提前拦截的死代码；
  新增设置覆盖链路测试（PATCH 保存 → 视图回显 → 消费 4/0→min(3,8)/cap 8/1=串行）。
- **真实 API 冒烟**（见 §3.6.6）：甜点 4（约 3.0x 加速、6/6 成功）；8 约 5.0x 但 2/6 失败（上游限流）。
- **已知坑（导入顺序）**：进程首个导入若为 `app.services.graph_sync` 会触发循环导入
  （graph_sync → clustering → graph/__init__ → cross_book → graph_sync 未定义 link_graph_assets）；
  生产由 routes 先导入 `app.services.graph.cross_book` 规避。外部脚本/测试需先导入 cross_book。
